**Goal:** Negotiate the TN3270E telnet option (40) with DEVICE-TYPE and FUNCTIONS subnegotiation, wrap and unwrap the 5-byte data header, answer host response requests, and select an LU by name — defaulting on, and falling back to traditional tn3270 when a host refuses.

**Architecture:** One new pure module, `packages/core/src/tn3270e.ts`, holding the negotiation state machine and the header codec as functions over byte arrays with no socket knowledge. `telnet.ts` gains an option-40 arm that routes subnegotiation bodies to it; `session.ts` holds the resulting state, prepends the header on the way out and strips it on the way in. The header is prepended *before* `sendRecord`, so it passes through the existing `doubleIac` and the RFC's IAC-escaping requirement is satisfied by construction rather than by a second implementation.

**Tech Stack:** TypeScript (ES2023, NodeNext), vitest, Node 26. No new dependencies.

```typescript
/**
 * TN3270E subnegotiation operations (RFC 2355 §3, rfc2355.txt:317-347).
 *
 * THE OPERAND ORDER IS ASYMMETRIC AND MISORDERING IT FAILS SILENTLY. The server
 * sends SEND then DEVICE_TYPE (0x08 0x02); the client replies DEVICE_TYPE then
 * REQUEST (0x02 0x07). x3270 pins the layout at telnet.c:2199, where the test is
 * `sbbuf[2] == TN3270E_OP_DEVICE_TYPE` — so sbbuf[1] is the verb. Sending
 * 0x02 0x08 was tried during design: real s3270 logged `DEVICE-TYPE ??8` and then
 * stalled, with no reject and no error.
 */
export const Tn3270eOp = {
  ASSOCIATE: 0x00,
  CONNECT: 0x01,
  DEVICE_TYPE: 0x02,
  FUNCTIONS: 0x03,
  IS: 0x04,
  REASON: 0x05,
  REJECT: 0x06,
  REQUEST: 0x07,
  SEND: 0x08,
} as const;

/** DEVICE-TYPE REJECT reason codes (RFC 2355 §3). */
export const Tn3270eReason = {
  CONN_PARTNER: 0x00,
  DEVICE_IN_USE: 0x01,
  INV_ASSOCIATE: 0x02,
  INV_NAME: 0x03,
  INV_DEVICE_TYPE: 0x04,
  TYPE_NAME_ERROR: 0x05,
  UNKNOWN_ERROR: 0x06,
  UNSUPPORTED_REQ: 0x07,
} as const;

/**
 * Negotiable functions. CONTENTION_RESOLUTION (0x05) is NOT in RFC 2355 — it is a
 * later extension, requested by x3270 at telnet.c:953. We request it for parity;
 * nothing in stage 2b depends on a host granting it.
 *
 * SCS_CTL_CODES and DATA_STREAM_CTL are printer-session functions by definition
 * (RFC 2355 §7.2.2) and belong to the printer stage. BIND_IMAGE is defined here
 * but deliberately NOT requested — see the design doc: granting it and then
 * receiving no BIND leaves a client out of 3270 mode entirely.
 */
export const Tn3270eFunc = {
  BIND_IMAGE: 0x00,
  DATA_STREAM_CTL: 0x01,
  RESPONSES: 0x02,
  SCS_CTL_CODES: 0x03,
  SYSREQ: 0x04,
  CONTENTION_RESOLUTION: 0x05,
} as const;

/** Header DATA-TYPE values (RFC 2355 §8.1.1). `DATA_3270` cannot be `3270_DATA`. */
export const Tn3270eDataType = {
  DATA_3270: 0x00,
  SCS_DATA: 0x01,
  RESPONSE: 0x02,
  BIND_IMAGE: 0x03,
  UNBIND: 0x04,
  NVT_DATA: 0x05,
  REQUEST: 0x06,
  SSCP_LU_DATA: 0x07,
  PRINT_EOJ: 0x08,
} as const;

/** Header REQUEST-FLAG (RFC 2355 §8.1.2). Meaningful only when DATA-TYPE is REQUEST. */
export const Tn3270eRequestFlag = { ERR_COND_CLEARED: 0x00 } as const;

/**
 * Header RESPONSE-FLAG (RFC 2355 §8.1.3). The field is overloaded by DATA-TYPE:
 * on 3270-DATA/SCS-DATA it says whether a response is wanted, and on RESPONSE it
 * says whether this IS a positive or negative one. POSITIVE_RESPONSE and
 * NO_RESPONSE therefore share the value 0x00 legitimately.
 */
export const Tn3270eResponseFlag = {
  NO_RESPONSE: 0x00,
  ERROR_RESPONSE: 0x01,
  ALWAYS_RESPONSE: 0x02,
  POSITIVE_RESPONSE: 0x00,
  NEGATIVE_RESPONSE: 0x01,
} as const;

/**
 * The one data byte of a RESPONSE message (RFC 2355 §10.4.1, rfc2355.txt:1440-1462).
 * DEVICE_END and COMMAND_REJECT share 0x00 because the meaning comes from
 * RESPONSE-FLAG: 0x00 under POSITIVE is "successful completion", under NEGATIVE it
 * is "an invalid 3270 command was received".
 *
 * The printer senses (0x01 "printer not ready", 0x03 "printer powered off") are
 * omitted: they are unreachable from a display session.
 */
export const Tn3270eSense = {
  DEVICE_END: 0x00,
  COMMAND_REJECT: 0x00,
  OP_CHECK: 0x02,
} as const;
```

```typescript
  it('decodes a header and returns the remaining payload offset', () => {
    const rec = Uint8Array.of(0x00, 0x00, 0x02, 0x00, 0x07, 0x7d, 0x40, 0xc2);
    expect(decodeHeader(rec)).toEqual({
      dataType: Tn3270eDataType.DATA_3270,
      requestFlag: 0x00,
      responseFlag: Tn3270eResponseFlag.ALWAYS_RESPONSE,
      seq: 0x0007,
    });
  });
```

```typescript
/**
 * TN3270E (RFC 2355): the option-40 subnegotiation state machine and the 5-byte
 * data header codec.
 *
 * Pure by design — bytes in, decisions and bytes out, no socket and no session.
 * The negotiation is the part most likely to be wrong, and a pure function can be
 * driven directly with the transcript recorded from real s3270 in
 * docs/superpowers/specs/2026-08-27-stage2b-tn3270e-design.md.
 */
import { Tn3270eDataType } from './constants.js';

/** RFC 2355 §8.1: DATA-TYPE, REQUEST-FLAG, RESPONSE-FLAG, then 2-byte SEQ-NUMBER. */
export const TN3270E_HEADER_BYTES = 5;

export interface Tn3270eHeader {
  dataType: number;
  requestFlag: number;
  responseFlag: number;
  seq: number;
}

/**
 * Build the true header bytes.
 *
 * DELIBERATELY DOES NOT ESCAPE 0xFF. RFC 2355 §8.1.4 requires that a 0xff inside
 * SEQ-NUMBER be doubled, and it will be — by `doubleIac()` in telnet.ts, which
 * every outbound record already passes through. Escaping here too would double it
 * twice and corrupt the sequence number. Prepend this to the payload and hand the
 * whole thing to `sendRecord`, and the requirement is met by construction.
 */
export function encodeHeader(h: Tn3270eHeader): Uint8Array {
  return Uint8Array.of(
    h.dataType & 0xff,
    h.requestFlag & 0xff,
    h.responseFlag & 0xff,
    (h.seq >> 8) & 0xff,
    h.seq & 0xff,
  );
}

/**
 * Read a header off the front of an inbound record, or null if the record cannot
 * hold one.
 *
 * A record of exactly five bytes is valid and carries no data: RFC 2355 §8 permits
 * `<TN3270E Header><IAC EOR>`, which is how PRINT-EOJ arrives. Returning null on a
 * short record rather than throwing lets the caller trace and drop it, which is
 * what a client should do with a malformed record from a host it cannot correct.
 */
export function decodeHeader(record: Uint8Array): Tn3270eHeader | null {
  if (record.length < TN3270E_HEADER_BYTES) return null;
  return {
    dataType: record[0]!,
    requestFlag: record[1]!,
    responseFlag: record[2]!,
    seq: (record[3]! << 8) | record[4]!,
  };
}

/** True for the data types that carry a 3270 datastream we can execute. */
export function carriesDatastream(dataType: number): boolean {
  return dataType === Tn3270eDataType.DATA_3270;
}
```

```typescript
import { Tn3270eFunc, Tn3270eOp } from './constants.js';

/**
 * The functions we ask for.
 *
 * BIND-IMAGE IS DELIBERATELY ABSENT, and the reason is a measured hazard rather
 * than cost. Granted BIND-IMAGE and sent no BIND, real s3270 never enters 3270
 * mode: an Erase/Write is delivered and ignored and Wait(3270Mode) times out.
 * Granting it with a BIND works, and denying it works. Since only the
 * advertise-then-stay-silent case hangs, not asking is what stops a server from
 * putting us there. x3270 accepts that risk (telnet.c:949-953); we need not.
 *
 * The two printer functions (SCS-CTL-CODES, DATA-STREAM-CTL) are printer-session
 * functions by RFC 2355 §7.2.2 and belong to the printer stage.
 */
export const REQUESTED_FUNCTIONS: readonly number[] = [
  Tn3270eFunc.RESPONSES,
  Tn3270eFunc.SYSREQ,
  Tn3270eFunc.CONTENTION_RESOLUTION,
];

export type Tn3270ePhase =
  | 'idle'
  | 'awaitingDeviceType'
  | 'awaitingFunctions'
  | 'negotiated'
  | 'backedOff';

export interface Tn3270eState {
  readonly phase: Tn3270ePhase;
  /** Functions agreed. Empty and phase 'negotiated' is "basic TN3270E" (§9). */
  readonly agreed: readonly number[];
  readonly terminalType: string;
  /** LU names still to try, in order. Consumed on REJECT. */
  readonly lus: readonly string[];
  readonly luIndex: number;
  readonly deviceType?: string;
  /** The LU the server reported, which need not be one we asked for. */
  readonly lu?: string;
}

export type Tn3270eEffect =
  | { kind: 'complete'; agreed: readonly number[] }
  | { kind: 'backoff'; why: string };

export interface NegotiateResult {
  readonly next: Tn3270eState;
  /** Subnegotiation body to send, option byte NOT included. Caller frames it. */
  readonly reply?: Uint8Array;
  readonly effect?: Tn3270eEffect;
}

export function initialState(o: { terminalType: string; lus: readonly string[] }): Tn3270eState {
  return {
    phase: 'idle', agreed: [], terminalType: o.terminalType,
    lus: o.lus, luIndex: 0,
  };
}

const ascii = (s: string): number[] => Array.from(s, (c) => c.charCodeAt(0) & 0xff);
const fromAscii = (b: Uint8Array): string => String.fromCharCode(...b);

/** Build DEVICE-TYPE REQUEST <ttype> [CONNECT <lu>]. */
function deviceTypeRequest(st: Tn3270eState): Uint8Array {
  const lu = st.lus[st.luIndex];
  return Uint8Array.from([
    Tn3270eOp.DEVICE_TYPE, Tn3270eOp.REQUEST, ...ascii(st.terminalType),
    ...(lu === undefined ? [] : [Tn3270eOp.CONNECT, ...ascii(lu)]),
  ]);
}

/**
 * Advance the negotiation by one received subnegotiation body.
 *
 * `body` excludes the option byte and the IAC SE, so `body[0]` is the first
 * operation. An unrecognized or misordered body yields no reply and no state
 * change: silence is the correct response to a message we cannot parse, and it is
 * what real s3270 does when handed a misordered SEND DEVICE-TYPE.
 */
export function negotiate(st: Tn3270eState, body: Uint8Array): NegotiateResult {
  // SEND DEVICE-TYPE: the verb comes FIRST here (0x08 0x02). The client's reply
  // puts the noun first (0x02 0x07). That asymmetry is real -- x3270 pins it at
  // telnet.c:2199 -- and reversing it makes s3270 log "DEVICE-TYPE ??8" and stall.
  if (body[0] === Tn3270eOp.SEND && body[1] === Tn3270eOp.DEVICE_TYPE) {
    return { next: { ...st, phase: 'awaitingDeviceType' }, reply: deviceTypeRequest(st) };
  }

  if (body[0] === Tn3270eOp.DEVICE_TYPE && body[1] === Tn3270eOp.IS) {
    // DEVICE-TYPE IS <type> [CONNECT <name>] -- the CONNECT clause is optional.
    const rest = body.subarray(2);
    const sep = rest.indexOf(Tn3270eOp.CONNECT);
    const type = fromAscii(sep === -1 ? rest : rest.subarray(0, sep));
    const lu = sep === -1 ? undefined : fromAscii(rest.subarray(sep + 1));
    const next: Tn3270eState = {
      ...st, phase: 'awaitingFunctions', deviceType: type,
      ...(lu === undefined || lu === '' ? {} : { lu }),
    };
    return {
      next,
      reply: Uint8Array.from([
        Tn3270eOp.FUNCTIONS, Tn3270eOp.REQUEST, ...REQUESTED_FUNCTIONS,
      ]),
    };
  }

  return { next: st };
}
```

```typescript
const KNOWN_FUNCS: readonly number[] = Object.values(Tn3270eFunc);

/**
 * Decode a function list, discarding codes we do not know.
 *

 * function code from the list and continue normal functions negotiation." So an
 * unknown code is not an error and must not abort the session.

function decodeFuncs(list: Uint8Array): number[] {
  return [...list].filter((f) => KNOWN_FUNCS.includes(f));

/** True when `offered` contains nothing outside `REQUESTED_FUNCTIONS`. */
function addsNothing(offered: readonly number[]): boolean {
  return offered.every((f) => REQUESTED_FUNCTIONS.includes(f));
```

## Task 6: Wire option 40 into the telnet layer — and fix the mode gate

**READ THIS TASK BEFORE STARTING IT.** It contains the one change most likely to be
missed, and missing it makes a TN3270E session silently deliver nothing.

**RFC 2355 §4 (`rfc2355.txt:376-382`): binary and EOR are IMPLIED by TN3270E and are
not explicitly negotiated.** "Note that while they are not explicitly negotiated, the
equivalent of the Telnet Binary Transmission Option and the Telnet End of Record
Option is implied in the negotiation of the TN3270E Option. That is, a party to the
negotiation that agrees to support TN3270E is automatically required to support
bi-directional binary and EOR transmissions."

This was confirmed on the wire during design: the harness sent **only** `IAC DO
TN3270E` — never BINARY, never EOR — and real s3270 still entered 3270 mode and
framed its inbound record with `IAC EOR`.

Our `is3270Mode()` (`telnet.ts:93-99`) requires BINARY **and** EOR agreed in both
directions. Against such a host it returns `false` for the whole session, and then:

- `storeRecordByte` (`telnet.ts:249`) drops every inbound data byte, and
- `flushRecord` (`telnet.ts:332`) discards the accumulator on every `IAC EOR`.

The result is a fully negotiated TN3270E session that renders nothing at all, with a
trace full of `EOR received outside 3270 mode`. So the gate must widen.

```typescript
   * Advance TN3270E negotiation by one subnegotiation body.
   *
   * All the protocol logic lives in tn3270e.ts; this method only moves bytes and
   * applies effects, which is why the state machine can be tested without a socket.
   */
  private handleTn3270eSubneg(body: Uint8Array): void {
    this.e ??= initialState({
      terminalType: this.opts.terminalType ?? TERMINAL_TYPE,
      lus: this.opts.lus ?? [],
    });
    const r = negotiate(this.e, body);
    this.e = r.next;
    if (r.reply) this.telnet?.sendTn3270eSubneg(r.reply);
    if (r.effect?.kind === 'complete') {
      this.eSeq = 0;
      this.telnet?.setTn3270eNegotiated(true);
      this.trace.note(`TN3270E negotiated, functions: ${r.effect.agreed.join(',') || '(none)'}`);
    } else if (r.effect?.kind === 'backoff') {
      // Tell the host no and forget the option, so the classic BINARY/EOR route is
      // still reachable on this same connection. x3270's backoff_tn3270e().
      this.trace.note(`TN3270E abandoned: ${r.effect.why}`);
      this.e = undefined;
      this.telnet?.refuseTn3270e();
    }

    return this.e?.phase === 'negotiated';

   *
   * The header is PREPENDED and the whole thing handed to sendRecord, so it flows
   * through the existing doubleIac(). RFC 2355 §8.1.4 requires a 0xff inside
   * SEQ-NUMBER to be doubled, and doing it this way satisfies that by construction
   * rather than by a second escaping implementation that could drift.
   */

    if (!this.inTn3270e()) {
      this.telnet?.sendRecord(payload);
      return;

    if (this.e?.agreed.includes(Tn3270eFunc.RESPONSES)) {
      this.eSeq = (this.eSeq + 1) & 0x7fff;
    }
    this.telnet?.sendRecord(framed);
```

## Task 9: The RESPONSES function

The mapping, from RFC 2355 §10.4.1 (`rfc2355.txt:1409-1462`):

| inbound RESPONSE-FLAG | processing | we send |
|---|---|---|
| `NO_RESPONSE` (0) | either | nothing |
| `ERROR_RESPONSE` (1) | succeeded | nothing |
| `ERROR_RESPONSE` (1) | failed | `RESPONSE` / `NEGATIVE`, sense byte |
| `ALWAYS_RESPONSE` (2) | succeeded | `RESPONSE` / `POSITIVE`, `0x00` |
| `ALWAYS_RESPONSE` (2) | failed | `RESPONSE` / `NEGATIVE`, sense byte |

SEQ-NUMBER is **copied** from the message being answered, never generated. Sense byte is
`COMMAND_REJECT` (`0x00`) for an invalid command and `OP_CHECK` (`0x02`) for an illegal
buffer address or order sequence.

```typescript
  /**
   * Send a TN3270E RESPONSE message (RFC 2355 §10.4.1).
   *
   * `seq` is COPIED from the message being answered, and this path deliberately
   * does not go through sendInbound(): a response must not consume one of our
   * outbound sequence numbers, or our numbering drifts out of step with what the
   * host is acknowledging.
   */
  private sendResponse(seq: number, positive: boolean, sense: number): void {
    if (!this.e?.agreed.includes(Tn3270eFunc.RESPONSES)) return;
    const header = encodeHeader({
      dataType: Tn3270eDataType.RESPONSE,
      requestFlag: 0,
      responseFlag: positive
        ? Tn3270eResponseFlag.POSITIVE_RESPONSE
        : Tn3270eResponseFlag.NEGATIVE_RESPONSE,
      seq,
    });
    const msg = new Uint8Array(header.length + 1);
    msg.set(header, 0);
    msg[header.length] = sense;
    this.telnet?.sendRecord(msg);
  }
```

```typescript
    try {
      // ...existing body, unchanged...

        this.sendResponse(respond.seq, true, Tn3270eSense.DEVICE_END);
      }
    } catch (err) {
      if (err instanceof ParseError || err instanceof AddressError) {
        this.programCheck(PROG_INVALID_COMMAND, err.message);
        // RFC 2355's two reachable senses are finer-grained than our two program
        // check codes, so map from the ERROR rather than from the code: 0x00 is "an
        // invalid 3270 command was received", 0x02 is "an illegal 3270 buffer

        // the latter, even though both currently report program check 754.
        // DO NOT change the program check codes to match -- they are pinned by
        // goldens and by the live VM/370 measurement.
        if (respond && respond.responseFlag !== Tn3270eResponseFlag.NO_RESPONSE) {
          this.sendResponse(respond.seq, false,
            err instanceof ParseError ? Tn3270eSense.COMMAND_REJECT : Tn3270eSense.OP_CHECK);

      } else if (err instanceof ExecuteError) {

          this.sendResponse(respond.seq, false, Tn3270eSense.OP_CHECK);
        }
      } else {
        throw err;
      }
```

```typescript
/**
 * Split a host argument into prefixes, LU names, host and port.
 *
 * s3270's documented shape is `[prefix:][LUname@]hostname[:port]`, with prefixes
 * stacked one colon each -- `S:C:host` -- and multiple LUs comma-separated and
 * tried in order as rejections come back (telnet.c setup_lus/next_lu).
 *
 * Prefix recognition is deliberately restricted to SINGLE letters, because that is
 * what s3270 accepts: writing two together as `SC:host` is a syntax error there
 * ("double ':'"), and matching that is what keeps `hostname:port` from being read
 * as a prefix when the hostname happens to be one character long.
 */
export interface HostSpec {
  readonly host: string;
  readonly lus: readonly string[];
  /** Upper-cased single-letter prefixes, in the order written. */
  readonly prefixes: readonly string[];
  /** Left as text; the caller owns port validation and defaulting. */
  readonly portText: string | undefined;
}

export function parseHostSpec(raw: string): HostSpec {
  let rest = raw;
  const prefixes: string[] = [];
  // Single letter followed by a colon, repeatedly.
  for (;;) {
    const m = /^([A-Za-z]):(.*)$/.exec(rest);
    if (m === null) break;
    prefixes.push(m[1]!.toUpperCase());
    rest = m[2]!;
  }

  const lus: string[] = [];
  const at = rest.lastIndexOf('@');
  if (at !== -1) {
    const names = rest.slice(0, at).split(',');
    for (const n of names) {
      if (n === '') throw new Error('empty LU name in the LU list');
      lus.push(n);
    }
    rest = rest.slice(at + 1);
  }

  // A bracketed IPv6 literal owns its colons; only a colon AFTER the bracket is a
  // port separator.
  if (rest.startsWith('[')) {
    const close = rest.indexOf(']');
    if (close === -1) throw new Error('unterminated [ in host');
    const host = rest.slice(1, close);
    if (host === '') throw new Error('no host in the host argument');
    const tail = rest.slice(close + 1);
    const portText = tail.startsWith(':') ? tail.slice(1) : undefined;
    return { host, lus, prefixes, ...(portText === undefined ? { portText: undefined } : { portText }) };
  }

  const colon = rest.lastIndexOf(':');
  const host = colon === -1 ? rest : rest.slice(0, colon);
  const portText = colon === -1 ? undefined : rest.slice(colon + 1);
  if (host === '') throw new Error('no host in the host argument');
  return { host, lus, prefixes, portText };
}
```

**One thing this plan adds that the spec did not have:** Task 6's mode-gate widening.
RFC 2355 §4 makes binary and EOR implied rather than negotiated, so `is3270Mode()` as
written would return false for a whole TN3270E session and discard every record. The
spec should be amended to record it — it is a design-level fact, not an implementation
detail.

**Type consistency:** `Tn3270eState`, `negotiate`, `initialState`,
`REQUESTED_FUNCTIONS`, `encodeHeader`, `decodeHeader`, `carriesDatastream`,
`TN3270E_HEADER_BYTES`, `parseHostSpec`, `sendTn3270eSubneg`,
`setTn3270eNegotiated`, `refuseTn3270e`, `sendSysreq`, `sendInbound`, `sendResponse`,
`sysreq()` are each defined once and used with the same signature throughout.
`Tn3270eDataType.DATA_3270` is spelled that way everywhere, because `3270_DATA` is not
a legal identifier.
